Commits in the last thirty days, one row per project, busiest first. Under each row sits the last
thing I committed there. Below the busy rows, the projects that got nothing this month, dimmed,
with how long they have been quiet.

It sits under `ls ./work` on the home page, the tall card on the right, beside the featured
project and the featured post.

## What it replaced

The card before it was `oss '26`: projects shipped this year against a goal of six. It had
something to say until the goal was met. After that it was `8 / 6` every day until January. A
card that stops changing in August is a card people stop reading.

This one changes every week. The goal is still there, as the comment in the footer, which is the
size it deserved once it was met.

## Only projects, and every project

The rows come from the repositories that have a page in `/projects`, matched on the `github` URL
in each project's frontmatter. The profile README and coursework have commits too, but a row
under `ls ./work` with nothing to link to would be the one row that goes nowhere. A new project
joins the card the day its MDX lands. There is no list to keep in step.

The quiet ones are listed as well. A card that only showed the busy projects would say everything
is moving, and `wristkit, 56d ago` is the honest half of it. Both lists have a ceiling, five
busy and four quiet, because the card grows with every project that ships and its height has to
stay close to the column beside it.

## One request

The month's counts come from `contributionsCollection`. The quiet projects are not in it, since
they have no contributions in the window, so each project also gets an aliased `repository`
field (`r0`, `r1`…) in the same query for its last commit. Merges and the changesets release
commit are skipped, and so is anyone else's commit.

```ts
r0: repository(owner: $o0, name: $n0) {
  defaultBranchRef { target { ... on Commit { history(first: 20) { … } } } }
}
```

Owners and names are variables and never part of the query text. They come from frontmatter,
and a variable can't change the shape of a query.

Two details keep it cheap. The window starts at UTC midnight rather than exactly thirty days
ago. `from` is in the request body and the body is the cache key, so a timestamp accurate to the
millisecond would have cached nothing. And "3h" or "18d" is worked out on the server for each
request, after the cached fetch. Computed in the component, it would come out different on each
side of hydration.

## Four states, and the one that isn't a state

`loading` is the card with its rows in grey at their real sizes. The home page streams the card
in `<Suspense>`, so the featured project beside it never waits for GitHub.

`error` covers three failures: no `GITHUB_TOKEN`, a status that isn't 200, and a GraphQL error.
GitHub reports a bad login or a spent quota as a 200 with an `errors` array, so checking
`res.ok` alone misses it.

`empty` is the only one about the account and not the server: the request worked and there were
no commits this month.

A repository GitHub can't resolve, renamed or made private, is not a state. It comes back as
`null` next to an `errors` entry, and the card keeps going. That row loses its last commit and
shows a dash, and the rest of the card is untouched. The last quiet row in the `ok` demo is one
of those.

## The hover

Every row is a link, so every row answers the pointer. The row gets a faint version of an
editor's current-line highlight, with a thin mark in the gutter where git draws a changed line.
Its bar lights up and a glint runs along it once. Its count and commit line get a little
brighter, an arrow appears on the commit line to say it leaves the site, and pointing at the
commit itself underlines the message. A quiet row comes up from 70% to full.

The first version did more. The other rows faded back, and the big number rolled from the
month's total to the row's own count. Each part was defensible on its own. Together they were
too much for a card whose job is to be read, so those two went and the number stays put.

The glint is a fixed gradient translated across the bar, never a gradient string rebuilt per
frame. It runs out on hover and snaps back out of sight on leave, so it only ever travels one
way. Its colour is `--fg-on-brand`, the ink every theme guarantees is readable on the brand fill.

It is all CSS on `:hover` and `:focus-within`, with no state and nothing to re-render. Tailwind v4
puts `hover:` behind `@media (hover: hover)`, so a tap on a phone goes straight to the link. The
highlight and the gutter mark reach into the card's padding, and the text and the hit areas stay
put. Rows are padded instead of spaced apart, so the highlights meet and the pointer never lands
in a gap that belongs to no row.
